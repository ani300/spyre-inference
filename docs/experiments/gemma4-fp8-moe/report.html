Gemma 4: FP8 experts through the full inference engine

Model: RedHatAI/gemma-4-26B-A4B-it-FP8-dynamic, revision ed35d7abe5d940da41b4ff06eb482feb0be8cb44. Assessment: 2026-10-29, TP1, text backbone.

The integrated B path generates text with FP8 expert storage and FP8 expert matmuls. The single-sentence FP16 KV-cache case passed and answered “The capital of France is Paris.” Remaining batch/cache cases are in progress. All 30 layers load, and the default compiled transformer blocks remain enabled.

Why the FP8 path needs different padding

DL16 splits Gemma’s 2816 hidden values into four chunks of 704. Each hardware stick holds 128 bytes. Switch formats to see one chunk:

What changed

  • FP8 MoE method: replaces the unsupported compressed-tensors method with a Spyre implementation, reuses checkpoint expert loaders, folds Gemma's learned expert multiplier into the down-channel scale, and uploads gate/up/down directly as QFP8WT.
  • torch-spyre loader branch: extends _dma_to_spyre_fp8_kernel and its C++ data-conversion descriptor to rank-3 expert pools (also tested at rank 4). Source strides and offsets are respected; the destination uses canonical dense strides.
  • Persistent expert computation: on-device routing followed by for_each_tile over resident experts. Gate, up and down use FP8 × FP8 scaled_bmm, with DL16 output, scale compensation, GELU and reduction. No tokens are packed on CPU.
  • Engine bridge: preserves the separate compiled routing and persistent-expert regions through the opaque MoE call inside each compiled transformer block. Prefill and decode share one FP8 expert representation. Short batches are zero-padded to 128 rows inside the MoE and trimmed before returning.
  • Dense FP8 linear padding: Gemma's shared MLP down projection has K=2112, which occupies 16.5 FP8 sticks. Pad its checkpoint bytes and activation to 2176 before FP8 matmul. Compiler-inserted padding otherwise loses QFP8WT and the matmul planner fails.

The expert intermediate width is padded from 704 to 768. Checkpoint FP8 codes are never dequantized for storage or repacked on device by the integrated path. The original source expert parameters are released after upload. Per-output-channel scales remain separate from the FP8 codes.

Why the earlier packing issue was avoidable

The earlier prototype uploaded FP8 code values through temporary DL16 tensors and called qfp8wt on device. A whole pool exceeded that conversion kernel's per-core address span; four smaller pools worked. That was a limitation of the prototype's conversion route, not a requirement of checkpoint loading. The extended loader now packs the checkpoint bytes directly, exactly where FP8 linear weights are packed. The earlier claim that full-pool device packing blocked engine integration was too broad.

A roundtrip alone is insufficient: an incorrect layout can be inverted by the same incorrect descriptor. The loader tests therefore also consume the uploaded weights in an FP8 grouped matmul against an exact independent oracle. Source tensors with holes additionally exposed the need for canonical destination strides.

Reproduce

Use the two experiment branches with the current upstream bases: spyre-inference d69bc3f, torch-spyre f2bb1f8d. Both were re-fetched from upstream main for this assessment. Build and install the patched torch-spyre into the prepared inference venv; do not let uv sync restore the repository pins. Run only one hardware workload at a time. --eager-blocks is an optional diagnostic that leaves FP8 kernels compiled while using eager transformer-block orchestration. JSON records failures and output tokens; the matrix preserves commands, logs and nonzero exits. The smoke test forces 16 output tokens (ignore_eos=True), so text after an end-of-turn marker is not part of the natural answer. Successful generation is a smoke result, not a claim of model-quality parity or speedup. The AIOps trace uses its original prompts and a fixed generated-token budget, so this is integration coverage rather than the full serving benchmark.

Remaining limitations

TP1, Gemma's GELU/full-softmax routing, 128 experts and top-k 8 only. The bridge rejects unsupported recipes and parallel configurations. The model's vision/audio towers are outside this experiment.

Persistent decode computes all experts over padded rows, so it is a correctness workaround with substantial extra work. The native gathered FP8 decode path and shared chunk aliases still need compiler work. Neither the FP16 nor FP8 KV-cache choice removes that limitation, because expert storage is independent of the attention cache.

The original layer assessment preserves the staged decode path, four-pool persistent path, failing native compiler probes and their numerical results. Those baseline files predate the direct-loader and engine integration changes.
